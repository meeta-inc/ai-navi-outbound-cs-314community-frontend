# AI 코더 개발 워크플로우 지침

## 개요
이 문서는 AI 코더가 프론트엔드 개발 시 반드시 준수해야 할 개발 워크플로우를 정의합니다. 모든 기능 개발은 이 플로우를 엄격히 따라야 합니다.

## TDD 사이클 원칙

### RED → GREEN → BLUE 사이클
1. **RED**: 테스트 케이스 작성 후 실패 확인
   - 테스트 케이스는 구현을 실행하기 전에 실패하는 것(RED)은 바람직함
   - **중요**: 케이스의 내용과 관계없는 설정 등에 의한 에러 발생은 테스트 케이스 작성 단계에서 수정
   
2. **GREEN**: 구현을 통해 테스트 통과
   - 구현은 반드시 테스트가 모두 성공할때까지(GREEN) 진행
   - 모든 테스트가 통과할 때까지 구현/수정 반복
   
3. **BLUE**: 리팩토링 (최종 점검 단계)
   - 최종 점검 단계에서 린트는 일단 무시 (추후 리팩토링 예정)
   - 기능 구현 완료 후 코드 품질 개선

## 핵심 개발 플로우

### 1. 컴포넌트 테스트 케이스 작성
**목적**: 구현하기 전에 테스트를 작성하여 요구사항을 명확히 하고 TDD 방식으로 개발

**작업 내용**:
- 컴포넌트의 예상 동작을 테스트 케이스로 작성
- Props에 따른 렌더링 결과 검증
- 사용자 인터랙션에 대한 반응 테스트
- Edge case 및 에러 상황 테스트

**예시**:
```typescript
describe('ChatInput 컴포넌트', () => {
  it('disabled가 true일 때 입력창이 비활성화되어야 한다', () => {
    // 테스트 케이스 작성
  });
  
  it('학년 미선택 시 적절한 플레이스홀더가 표시되어야 한다', () => {
    // 테스트 케이스 작성  
  });
});
```

### 2. 컴포넌트 테스트 실시
**목적**: 작성한 테스트가 올바르게 실행되는지 확인

**작업 내용**:
- `npm test -- 컴포넌트명.test.tsx` 명령어로 테스트 실행
- 테스트 실패 확인 (Red 단계)
- 테스트 환경 설정 문제 해결

**명령어 예시**:
```bash
npm test -- src/components/organisms/ChatInput/ChatInput.test.tsx
```

### 3. 컴포넌트 테스트 성공할 때까지 구현/수정
**목적**: 테스트를 통과하는 최소한의 구현으로 기능 완성

**작업 내용**:
- 실패하는 테스트를 하나씩 통과시키도록 구현
- 코드 품질을 유지하면서 기능 구현
- 모든 테스트가 통과할 때까지 반복

**주의사항**:
- 테스트를 통과하기 위해 임시방편적인 코드 작성 금지
- 기존 기능을 해치지 않도록 회귀 테스트 확인

### 4. 스토리북 작성
**목적**: 컴포넌트의 다양한 상태와 사용법을 문서화

**작업 내용**:
- 컴포넌트의 기본 상태 스토리 작성
- Props 변화에 따른 다양한 상태 스토리 추가
- 실제 사용 시나리오 기반 스토리 작성
- 접근성 및 반응형 대응 상태 스토리

**예시**:
```typescript
export const GradeNotSelected: Story = {
  args: {
    value: '',
    disabled: true,
    placeholder: 'まずは学年を選択してください',
  },
  parameters: {
    docs: {
      description: {
        story: '학년이 선택되지 않은 상태에서의 ChatInput 동작'
      }
    }
  }
};
```

### 5. 메인페이지 테스트 케이스 작성
**목적**: 컴포넌트가 실제 페이지에서 올바르게 동작하는지 통합 테스트

**작업 내용**:
- 페이지 레벨에서의 컴포넌트 통합 테스트 작성
- 상태 관리 및 Props 전달 로직 테스트
- 사용자 시나리오 기반 통합 테스트

### 6. 테스트 실행
**목적**: 전체 애플리케이션 레벨에서 기능이 올바르게 동작하는지 검증

**작업 내용**:
- 메인페이지 테스트 실행
- 컴포넌트 단위 테스트와 통합 테스트 모두 통과 확인

### 7. 메인페이지 포함 테스트 통과하게 소스 수정
**목적**: 실제 구현체에서 테스트가 통과하도록 코드 수정

**작업 내용**:
- MainPage 컴포넌트에서 Props 전달 로직 구현
- 상태 관리 로직 추가
- 플레이스홀더 및 disabled 상태 제어 구현

**예시**:
```typescript
// MainPage.tsx에서 ChatInput에 전달할 props 구현
<ChatInput
  value={newMessage}
  onChange={setNewMessage}
  onSend={handleSendClick}
  disabled={isTyping || (showGradeSelection && !selectedGrade)}
  placeholder={getPlaceholderText()}
  onMenuItemClick={handleMenuItemClick}
/>
```

### 8. 최종 점검 (make all-tests)
**목적**: 전체 프로젝트의 테스트가 모두 통과하는지 최종 확인

**작업 내용**:
- `make all-tests` 명령어로 전체 테스트 스위트 실행
- 단위 테스트 모두 통과 확인
- 빌드 프로세스 정상 동작 확인
- **린트 에러는 일단 무시** (추후 리팩토링 단계에서 처리 예정)

**명령어**:
```bash
make all-tests
```

**주의사항**:
- 테스트 실패 시 해당 단계로 돌아가서 수정
- 린트 경고/에러는 기능 구현 완료 후 별도 리팩토링 단계에서 해결
- 빌드 실패 시 의존성 및 타입 에러 우선 해결

## 준수사항

### 필수 규칙
1. **테스트 우선 개발**: 구현 전에 반드시 테스트 케이스를 먼저 작성
2. **순차적 진행**: 위 8단계를 순서대로 진행하며 이전 단계 완료 후 다음 단계 진행
3. **테스트 통과**: 각 단계에서 테스트가 통과하지 않으면 다음 단계로 진행 금지
4. **문서화**: 스토리북을 통한 컴포넌트 사용법 문서화 필수

### 품질 기준
- **테스트 커버리지**: 새로 작성하는 코드는 80% 이상 커버리지 유지
- **타입 안전성**: TypeScript 컴파일 에러 0개 유지
- **린트 규칙**: ESLint 규칙 100% 준수
- **접근성**: WCAG 2.1 AA 수준 준수

### 금지사항
- 테스트 없이 구현 시작하는 것
- 실패하는 테스트를 무시하고 다음 단계로 진행하는 것  
- 임시방편적인 코드로 테스트를 통과시키는 것
- 스토리북 작성을 생략하는 것
- make all-tests 실행 없이 작업을 완료했다고 판단하는 것

## 트러블슈팅

### 테스트 실행 시 자주 발생하는 문제
1. **Mock 설정 오류**: 외부 의존성 Mock이 제대로 설정되지 않은 경우
2. **비동기 처리**: React 상태 업데이트가 act()로 감싸지지 않은 경우  
3. **모듈 경로**: import 경로가 잘못되어 모듈을 찾을 수 없는 경우

### 해결 방법
- Mock 설정은 테스트 파일 상단에 명시적으로 작성
- React 상태 변경은 항상 act()로 감싸기
- 상대 경로보다는 절대 경로 사용 권장

## 예외 상황
다음과 같은 경우에만 워크플로우 변경 가능:
- 긴급 버그 수정 (단, 수정 후 테스트 보완 필수)
- 외부 라이브러리 변경으로 인한 호환성 문제
- 프로젝트 마일스톤상 불가피한 일정 문제

**예외 상황에서도 최소한 단위 테스트는 반드시 작성해야 함**
